## 一、角色定位与职责边界

本端在四人团队中承担 **双前台 / 一后台** 的复合职责，是全局的数据汇聚与管控中枢：

1. **统一认证中心（SSO）**——监管端数据库是全组登录的"主库"，为全组签发/验证 JWT。群众端、审批员端、企业端共用同一套 `sys_user/sys_role`，用相同密钥本地验证 Token，不跨库查表。
2. **监管数据汇聚方**——通过 RabbitMQ 接收审批端推送的审批结果数据（接口契约 9），落入 `approval_data_cache`，作为大屏统计与风险预警的数据源。
3. **监管/管理后台**——用户、角色、权限管理 + 企业/个人信用评价 + 风险预警 + 抽样检查 + 审计追溯 + 统计大屏（ECharts，配 WebSocket 实时推送）。

**边界原则（必须遵守）**：
- 只用本端 Schema `govai_supervision`，**不允许跨 Schema 直查**其他三端数据。
- 需要他人数据时，通过文档第 5 节定义好的 9 个跨服务接口契约（Feign / MQ / HTTP）获取。
- 第 1–5 周开发阶段不依赖 Nacos，Feign 用 URL 直连 + Fallback Mock；第 6 周联调阶段切换 Nacos 服务发现。

## 四、后端模块划分（包结构 `com.govai.supervision`）

> 📌 **结构优化建议**：当前骨架包名为 `com.yxy.supervision`。为贴合文档 8.2 统一规范（`com.govai.supervision` / `GovAiSupervisionApplication`），建议包名一并迁移，保持后端包名与文档一致。如团队允许可保留原包名，但强烈建议统一。

```

    ├── dto/  vo/                            # 请求/响应、视图对象

    ├── controller/                         # REST 接口

    ├── mq/                                 # RabbitMQ 消费器（approval.record.queue）

└── src/main/resources/

### 4.1 后端功能清单（REST 接口编排按文档 4 命名规范）

**认证模块**（跨服务契约 1/2，must-pass 第 1 周）
- `POST /api/v1/auth/login` —— 统一登录，按 `loginType` 区分（CITIZEN/ENTERPRISE/APPROVER/SUPERVISOR），校验 `sys_user`，签发 JWT
- `GET  /api/v1/auth/verify` —— Token 验证，供全组调用

**用户权限模块**
- `GET  /api/v1/users/list`、`GET /api/v1/users/{id}`、`POST /api/v1/users`、`PUT /api/v1/users/{id}`、`DELETE /api/v1/users/{id}` —— 用户 CRUD
- `GET  /api/v1/users/{id}/reset-password`（特殊操作）等
- 角色/权限 CRUD：`/api/v1/roles`、`/api/v1/permissions`，含角色授权、权限树

**信用模块**
- 企业信用查询/评价：`/api/v1/credit/enterprise`
- 个人信用：`/api/v1/credit/personal`
- 信用修复：`/api/v1/credit/repair`（提交 → 待审核 → 通过/驳回）

**风险预警模块**
- 规则管理：`/api/v1/risk/rules`（CRUD，TIMEOUT/ANOMALY/THRESHOLD）
- 预警记录：`/api/v1/risk/alerts`（查询、处置）

**监管业务模块**
- 抽样检查：`/api/v1/samples`（RANDOM/TARGETED）
- 审计追溯：`/api/v1/audit/traces`（按 instanceId 全链路回溯）

**统计大屏**
- `/api/v1/stats/overview`、`/api/v1/stats/daily` 等汇总接口
- WebSocket 实时推送（/ws 端点）

**通用**
- `/api/v1/auth/dicts`、操作日志 `/api/v1/logs`

## 五、前端规划（govai-supervision-ui，Vue3 + TS + Element Plus + ECharts）

前端为 **大屏 + PC 后台** 双形态，特色依赖为 WebSocket。

```
govai-supervision-ui/
├── package.json
└── src/
    ├── pages/        # 页面
    ├── api/          # 接口请求（编排对应后端 REST）
    ├── stores/       # Pinia（用户/token、菜单、大屏数据）
    ├── components/   # 大屏图表（ECharts）、通用表格组件
    ├── router/       # 路由 + 权限守卫
    ├── utils/        # WebSocket 封装等
    └── layout/       # 大屏布局 / 后台布局

**页面清单**
1. 登录页（对接 `POST /api/v1/auth/login`）
2. 大屏首页（ECharts：实时统计、认证量、办结量、超时量、满意率、时序走势；WebSocket 实时刷新）

4. 信用评价页（企业 / 个人 / 修复审核）
5. 风险预警页（预警列表、处置）
6. 抽样检查 / 审计溯回页
7. 系统设置（字典、操作日志）

## 六、与全组接口契约（本端提供 / 消费）

### 本端提供
- `POST /api/v1/auth/login`（契约 1）
- `GET  /api/v1/auth/verify`（契约 2）

### 本端消费（跨服务，第 6 周 Nacos 联调）
- 审批端 → 本端：`POST /api/v1/ai/summary`（契约 7，数据摘要）
- 审批端 → 本端：**RabbitMQ** `approval.record.push`（契约 9，关键：本端需在 `application.yml` 中配置 MQ）

```
交换机: approval.exchange
路由键: approval.record.push
队列:   approval.record.queue
监听 → 写入 approval_data_cache 表
```

### 外部依赖等待他人
- 联调时我端需要**审批端** / **群众端**已实现各自接口。

## 八、风险点与应对

1. **包名不一致**：当前 `com.yxy.supervision` vs 文档 `com.govai.supervision` → 统一调整包名。
2. **Spring Boot 版本差异**：骨架 Spring Boot 4.1.1（兼容性待定），需评估降级到 3.2.5 以匹配全组与 MyBatis-Plus/Knife4j 版本兼容。
3. **JWT 密钥**：生产必须改用强密钥并统一管理，本地服务 spring 需与文档一致。
4. **密码散列**：预置 `$2a$10$xxx` 明文函数——需替换为真实 BCrypt 值。
5. **MQ 环境**：本地需提供 RabbitMQ；第 6 周联调前需向审批端（张可）确认 交换机/队列命名一致的约定。
